| R-01 | Major | `packages/db/src/catalog/catalog-service.ts` > méthode `searchProducts` ligne 179 | La requête SQL utilise `LIKE '%' \|\| ? \|\| '%'` (wildcard en tête), ce qui **bypasse** l'index B-tree `products_tenant_search_idx` créé en migration v3. La `performance-design.md` affirme « le main applique BR3.4 en SQL/index, pas en filtrant 10k lignes en JS » — or le SQL fait un full-scan de la colonne `search_normalized` filtrée par `tenant_id` et `active`. Pour 10 000 articles le scan reste probablement sous les 200 ms ENF-02, mais la revendication "index lookup" du design est inexacte et aucun ADR ni note dans le code ne documente ce choix conscient. | Soit ajouter un index FTS5 virtuel (migration réversible) et réécrire la requête, soit conserver le LIKE et (a) amender la `performance-design.md` pour remplacer « en SQL/index » par « full-scan `search_normalized`, acceptable jusqu'à N articles — cible ENF-02 vérifiée à J1 », et (b) ajouter un commentaire dans `catalog-service.ts` expliquant le choix. Dans tous les cas, mettre à jour le traceability NFR3.1 pour refléter l'implémentation réelle. | New |
| R-02 | Major | `docs/adr/` — aucun fichier `004-*.md` n'existe ; `packages/db/src/migrations.ts` > migration v3 `catalog-search-normalized` | La migration v3 ajoute la colonne `search_normalized` et l'index `products_tenant_search_idx` à la table `products`. `team.md` mandate explicitement : « Tout nouveau module natif, tout adaptateur de reconnaissance d'image, et **tout changement de schéma catalogue ont leur ADR** ». Aucun ADR n'a été créé pour ce changement de schéma. | Créer `docs/adr/004-catalog-search-normalized.md` documentant : contexte (fragment search BR3.4), décision (colonne dénormalisée + LIKE ou FTS5), alternatives considérées et raison du choix, conséquences (migration réversible v3↓ documentée). | New |
| R-03 | Minor | `packages/db/src/migrations.ts` > migration v3 `catalog-search-normalized`, bloc `up`, instruction `UPDATE products` | Le `UPDATE` de rattrapage utilise `lower()` SQL de SQLite, qui ne replie pas les accents (é → e, ç → c, etc.). La fonction domaine `normalizeSearchText` (BR3.4) fait ce repliage avec `ACCENT_MAP`. Les produits existants migrés de v2 → v3 auraient un `search_normalized` incomplet (pas de repliage accents), rendant la recherche « Ecrou » incapable de retrouver « Écrou » pré-existant. En C1 il n'y a pas de produits pré-v3, donc aucun impact immédiat, mais c'est une bombe à retardement pour C2+ si des produits existent avant la migration. | Remplacer le `UPDATE` par une migration qui appelle la logique de normalisation, ou documenter explicitement la limitation (ex. comment dans la migration : « Rattrapage partiel – sans repliage accents ; les produits insérés après v3 sont corrects via `buildSearchNormalized`. ») et créer un script de re-normalisation facultatif. | New |
| R-04 | Minor | `packages/domain/src/catalog/product-create.ts` > interface `MinimalProductInput` ligne 14 | L'interface déclare `readonly internalCode?: string` mais `validateMinimalProductCreate` n'utilise jamais ce champ. La validation du `internalCode` (unicité, génération auto) est réalisée séparément par `resolveInternalCode` dans la couche DB. Ce champ fantôme dans `MinimalProductInput` crée une API trompeuse : un appelant peut penser que passer `internalCode` le valide, alors que la fonction l'ignore silencieusement. | Retirer `internalCode` de `MinimalProductInput` (le champ ne doit pas figurer dans l'interface de la règle purement métier `validateMinimalProductCreate`) ; si on souhaite valider l'ensemble fiche+code en domaine, créer une interface `FullProductInput` distincte ou documenter clairement la séparation des responsabilités. | New |

### Summary

Le Bolt C1 est fonctionnellement correct et livrable : typecheck, lint et test passent, la couverture domain dépasse 95 %, l'atomicité outbox est prouvée, le masquage vendeur est défendu en trois couches, et tous les invariants critiques (UUID v7, tenant_id, append-only audit/outbox, aucun flottant, aucun secret) sont respectés.
